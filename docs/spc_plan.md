# SPC（スーパーファミコン）の MIDI 化 計画（2026-11-03、コード変更なし）

## NSF / GBS との違い

| | NSF / GBS | SPC |
|:---|:---|:---|
| 音源 | 矩形波・三角波・ノイズ（音程はレジスタから計算） | 8 ボイスのサンプル再生（BRR 形式の波形を任意の速さで再生） |
| 音程 | 周期レジスタ → そのまま周波数 | ピッチレジスタは「元の速さの何倍で再生するか」だけ。**音程を出すにはサンプル自体の音高が必要** |
| 発音 | 周期上位レジスタの書き込み・音量の立ち上がりなどから推定 | **KON（キーオン）レジスタがある**ので発音の開始ははっきり分かる |
| 音色 | duty 比程度 | ボイスごとに使うサンプル番号（SRCN）。曲の途中で変わる |
| ドラム | ノイズ・DPCM | ドラムのサンプル（キック・スネア・ハイハット…）を普通のボイスで鳴らす。ノイズ発生器もある |
| 再生 | INIT / PLAY を 1/60 秒ごとに呼ぶ | SPC700 という CPU がずっと動き続け、タイマーを見ながら DSP レジスタを書く |
| ファイル | 曲データ＋ドライバ | **APU のメモリ 64KB とレジスタのスナップショット**（ある瞬間の状態から再開） |

## 全体の流れ（案）

1. **SPC を読む**: 64KB の RAM・DSP レジスタ・SPC700 のレジスタ、ID666 タグ（曲名・長さ）
2. **SPC700 をエミュレートして DSP への書き込みを記録**（NSF の 6502 と同じ考え方）
   - KON / KOFF、ピッチ（P）、サンプル番号（SRCN）、音量（VOL L/R）、ADSR / GAIN、ノイズ（NON）
3. **サンプルの音高を推定**: サンプル表（DIR）から BRR を復号し、ループ部分の 1 周期を自己相関で求める
   （DPCM の音程推定 v0.1.24 と同じ方法）。音高 = 32000 Hz ÷ 周期 × P / 0x1000
4. **ノート化**: KON = 発音開始。終わりは KOFF・次の KON・エンベロープが 0 になる所・ループしないサンプルの終わり
5. **トラック分け**: ボイス N → MIDI ch N（morokoshi の SPC のチャンネルボタン 1〜8 と同じ）。
   **同じボイスでサンプルが変わったら別トラック（同じ ch）**（ユーザー案。DPCM の音程付きトラックと同じ形）。トラック名は「Ch3 S12」のようにサンプル番号（楽器名は Sibelius が楽器と誤認するので使わない）
6. **ドラム**: サンプルごとに打楽器かどうかを判定し、GM のノート番号に置き換える（下記）
7. **テンポ・拍子・ループ**: NSF と同じ tempo.py / loop.py / meter.py を使う（発音時刻を 1/60 秒単位などに直して渡す）

## ドラムの考え方

- 判定は **サンプル単位**（同じサンプルは同じ打楽器）。特徴:
  - ループしない（または短いノイズのループ）、音の長さ、明るさ（ゼロ交差・スペクトル重心）、音程のはっきりさ（自己相関の強さ）
  - 低くて短い → キック、中域でノイズ的 → スネア、高くて短い → ハイハット、高くて長い → クラッシュ・ライド
  - 音程がはっきりしていて減衰する音を複数の音程で鳴らす → タム（音程付き。NES の下降音ドラム・DPCM の音程付きトラックと同じ扱い）
- ノイズ発生器（NON）を使うボイスはハイハット・シンバル系
- 判定は経験則なので、**サンプル番号 → GM ノートの上書き指定**を用意（NES の `--drum-map` と同じ考え）
- 出力: ドラムと判定したサンプルは、そのボイスの ch の「ChN Drums」トラック（NES のノイズ ch4・DPCM ch5 と同じ考え）。
  まとめて ch 10 に出すかは要相談

## 技術的な課題

- **SPC700 の速さ**: CPU が常に動き続ける（約 100 万命令/秒）ので、Python では NSF の 8 倍前後の処理量。
  ドライバはタイマー待ちのループで多くの時間を使うので、**待ちループを検出して時間を飛ばす**ことで速くできる見込み。
  遅すぎる場合の代案: morokoshi 用に改造している libgme の DLL に「DSP への書き込みを記録する」機能を足す（ただし nsf2mid 単体の配布物にも DLL が必要になる）
- **サンプルの音高のオクターブ誤り**: 自己相関は 1 オクターブ上下に間違えやすい（DPCM と同じ）。サンプルごとの移調指定（GUI で直せる形）を用意する
- **エンベロープ**: ADSR / GAIN を模型化しないと音の終わり（ゲート）が分からない。最初は KOFF・次の KON までとし、必要に応じて模型化
- **ビブラート・ポルタメント**: ピッチレジスタが連続で変わる。NES と同じく半音未満の揺れは同じ音、半音を超えて留まれば新しい音
- **テンポの単位**: NES の「1/60 秒の PLAY」がない。ドライバのタイマー（T0 など）の周期を「フレーム」として使えるか調べる。ダメなら 1/60 秒に直す
- **エコー・ピッチモジュレーション**: MIDI には出さない

## 進め方（段階）

1. **試作・調査**: SPC の読み込み、BRR の復号とサンプル表、SPC700 の模型と DSP 書き込みの記録。速さを測る。
   libgme で 1 ボイスずつ鳴らした音と、記録から出した音程を比べる（NES の拡張音源と同じ確認方法）。対象: スーパーマリオワールド・FF6・クロノ・トリガー など代表的なドライバ
2. **ノート化とトラック分け**（ボイス × サンプル）
3. **ドラム判定**
4. **テンポ・ループ・拍子**（既存の仕組みにつなぐ）
5. **GUI**（nsf2mid で .spc / SPC 入りの zip を開く）と morokoshi の Save → MIDI

## ユーザーの決定（2026-11-03）

1. MIDI ch は各ボイスの ch（ドラムも。他の音源と同じ）
2. トラックを分けるのはサンプル（音色）が変わったときだけ。音量・エンベロープでは分けない
3. サンプルの音高は自動推定でよい
4. 確認曲: FF4・FF5・FF6・アクトレイザー・ゼルダ（神々のトライフォース）・クロノ・トリガー

## 第 1 段階の結果（v0.1.36、2026-11-03）

- 新規 src/cpu_spc700.py（SPC700 の全 256 命令）、src/spc.py（SPC の読み込み・タイマー・DSP への書き込み記録・待ちループ飛ばし）、
  src/spc_dsp.py（BRR の復号・サンプルの音高推定・ボイスの状態）
- 速さ: 20 秒分を 1.2〜3.5 秒（実時間の 6〜16 倍）。待ちループ飛ばしが効いている
- 音程の確認（libgme で 1 ボイスずつ鳴らした音の基本周波数と、模型の音程を比較。20 秒、1/20 秒ごと）:
  - FF4「Red Wings」・FF6「Awakening」・アクトレイザー 2 曲・クロノ・トリガー 1 曲: 旋律・和音のボイスはほぼ全部一致（ずれは推定側の誤差と思われる少数）
  - 合わないボイスはドラムのサンプル（FF4 のサンプル 67・69、クロノのサンプル 38 など）→ 第 3 段階で打楽器として扱う
- サンプルの音高の推定方法:
  - 波形がはっきり繰り返す（自己相関 0.9 以上）サンプルは周期から
  - あいまいなサンプルは倍音の重なり（各倍音の対数スペクトルの和）から。1 オクターブ下も同程度に当てはまれば下を選ぶ
  - 例: FF5「A Presentiment」のサンプル 39 は 4・5 倍音が強く、周期の方法では 5 倍音を拾って 4 半音ずれていた → 倍音の方法で一致
  - 倍音の方法だけにするとアクトレイザーのサンプル 12 が 1 オクターブ上になったので、両方を組み合わせた
- 未対応（第 2 段階以降）: エンベロープ（ADSR / GAIN）・音の終わり、ノート化、トラック分け、ドラム、テンポ

## 第 2 段階の結果（v0.1.36、2026-11-03）

- nsf2mid.py に SPC を組み込み（CLI のみ。`python src/nsf2mid.py "Final Fantasy IV (EMU).zophar.zip" -t 2`）
  - zip 内の .spc を名前順に 1 曲目・2 曲目…（morokoshi と同じ）。nsf.open_player がファイルの先頭で NSF / GBS / SPC を切り替え
  - 8 ボイス = V1〜V8 = MIDI ch 1〜8。**同じボイスでサンプルが変わったら同じ ch の別トラック**（トラック名「Ch7 S67」など）。音量・エンベロープでは分けない
  - 発音 = KON。音の始まりはキーオンの正確な時刻（CPU サイクル。1/60 秒のフレームの途中も含む）
  - エンベロープの模型（spc_dsp.Voice）: ADSR（アタック・ディケイ・サステイン）・GAIN（直接・直線/指数の増減）・リリース（KOFF 後 -8/サンプル）、
    ループしないサンプルは再生し終えたら無音。音の終わり = エンベロープが 0
  - 変換のたびに最初から作り直していたフレームを、前回の続きから作る（FF4 の 300 秒分: 73 → 47 秒）
- 確認: FF4・FF5・FF6・アクトレイザー・ゼルダ・クロノ・トリガーの各 1 曲がエラーなく MIDI に。
  鳴っている区間は libgme とよく一致（模型だけが鳴っているフレームはほぼ 0。libgme だけのフレームは主にエコーの残響）
  - FF4「Red Wings」: Ch7 は途中で音色が変わり Ch7 S67・Ch7 S68 の 2 トラックに
- NES の回帰テストは変化なし
- 第 4 段階の課題（テンポ）: 音の始まりが毎回 ±0.4 フレームほど揺れ（ドライバーのテンポの累積の丸め）、テンポの判定が乱れる
  （FF4「Red Wings」は 1 拍 54 フレームのはずが 36 フレーム = 99 BPM と判定）。FF6「Opening Theme」はループを 2 秒と誤検出

## 第 3 段階の結果（v0.1.37、2026-11-03）: ドラム

- 新規 src/spc_drums.py。判定は**サンプル単位**、GM ノートは**1 打ごと**（同じサンプルでも鳴らす速さ＝ピッチレジスタで明るさ・長さが変わる）
- 打楽器のサンプル:
  - ループするサンプル: ループ部分がノイズ（周期の相関 < 0.5）で 3 音程以下 → シンバル
  - ループしないサンプル: ノイズ（相関 < 0.5）、または音程がはっきりしない（< 0.9）で 2 音程以下、
    または低くこもった音（実際の明るさ < 300 Hz。正弦波に近いキック・タム）で 3 音程以下、
    または C7 より上の 1〜2 音程だけ（楽器が使わない高さ）
  - ノイズ発生器（NON）を使っている音は全部（長さでハイハット・シンバル）
  - たくさんの音程で鳴らす単発サンプルは楽器（ピチカート・ベースなど）として残す
- GM ノート（鳴らす速さを掛けた明るさ・長さで）: ノイズのループ・500 ms 以上のノイズ → 49 クラッシュ、
  300 Hz 未満で 1 音程 → 36 キック、900 Hz 未満で音程あり → 45 ロータム（複数の音程なら低い順に 41〜50 のタム）、
  4500 Hz 未満 → 38 スネア、それより明るい → 140 ms 以下は 42 クローズ、長ければ 46 オープンハイハット、
  音程のはっきりした高い単発 → 56 カウベル
- 出力: そのボイスの ch の「ChN Drums」トラック（GM のノート番号）。音色ごとのトラックは楽器のサンプルだけ
- 上書き: `--drum-map "S67=38,S68=0"`（0 = ドラムにせず音符のまま）
- テンポ・ループの検出には、これまでどおり全部の音（ドラムを含む）を使う
- 確認（特徴の集計と結果。耳では未確認）:
  - FF4「Red Wings」: S67 スネア（マーチ）、S68 → タム（2 音程。ティンパニと思われる）、S69 クラッシュ
  - FF4「Fight 1」: S70 キック、S69 スネア、S68 クローズハイハット、S67 クラッシュ
  - FF6「Battle Theme」: S39 キック、S40 スネア、S36 クローズ・S37 オープンハイハット、S38 クラッシュ
  - クロノ「Battle 1」: S32 キック、S33 スネア、S34・S35 ハイハット、S37 タム、S36 クラッシュ
  - FF5「Mambo de Chocobo!」: S37 ハイハット、S38 スネア、S35 カウベル
  - アクトレイザー「Fillmoa」: S16 キック、S17 タム、S18 シンバル。ゼルダ「Hyrule Field」: S19 スネア、S2 キック（ティンパニ？）、S12 クラッシュ
  - ドラムのない曲（FF5「A Presentiment」、ゼルダ「Seal of Seven Maidens」、アクトレイザー「Sky Palast」）は全部楽器のまま
- NES の回帰テストは変化なし
- 不具合修正: 音高推定（倍音の方法）で、1 オクターブ下が探す範囲の外になるサンプルで止まっていた（FF6「Battle Theme」など）

## 第 3 段階の追加（v0.1.38、ユーザー指示）

- 異なる音色（サンプル、ノイズ発生器）に同じノート番号を割り当てない（spc_drums.unique_notes）。
  多く鳴る音色が本来の番号を使い、ほかは関連する空き番号へ（スネア 38 → 40・37・39、クローズハイハット 42 → 44・54、
  クラッシュ 49 → 57・52・55、キック 36 → 35、タム同士、カウベル 56 → 75・76・77）。それも埋まっていれば近い空き番号。
  同じサンプルが複数の番号を使うのは可（タム・鳴らす速さ）。--drum-map で指定したサンプルはその番号のまま

## 第 4 段階の結果（v0.1.38、2026-11-03）: テンポ・ループ

- 原因（FF4「Red Wings」）: 1 拍 = 27 フレームで、3 連（9 フレーム）・6 連（4.5 フレーム）・8 分（13.5）が並ぶ。
  4.5 フレームを 32 分として 1 拍 8 行（99 BPM）にしていた。さらにドライバーのテンポは途中で 1.4 % 遅くなり（48〜62 秒）、
  曲全体で 1 つの位相では細かい格子に乗らない
- 対策（SPC のときだけ。NES の結果は変えない）:
  - 格子の当てはまりを 4 秒ごとの位相で測る（tempo._drift_hits）
  - 1 拍 6 行の判定（tempo.sextuplet_beat）: 長い音（次の音まで 6 行以上）どうしの間隔が 6 行の倍数で、8 行の倍数より明らかに多い
  - 格子が整数倍で同じ区間（4.5 と 9.1）は分けない（tempo._multiple）。区間ごとの格子は近くで一番合うものを使う
  - 区間はすべて 1 小節ずつテンポを追う（tempo.track_rows_drift: 1 小節前の音からの間隔で単位を測るので、1 音ずつの揺れでは動かない）。
    テンポは 1 小節に 1 つ（1 % 未満の変化は書かない）
  - 区間ごとの 1 小節の繰り返しからのテンポ（v0.1.35）は SPC では使わない
- ループ（loop.detect_loop(strict=True)、SPC のみ）:
  - 自分の周期がないボイスでも、ループの中で鳴っていて繰り返さないなら、そのループは不採用（FF6「The Mines of Narshe」が 17 秒から 2.18 秒と誤検出していた）
  - 最初の音から繰り返すボイスは、その前の無音も繰り返しの一部（途中から加わるボイス。Narshe は 52 秒・70 秒から加わる 2 つのボイスでループ開始が 70 秒になっていた → 17.4 秒）
- 結果: Red Wings 132〜133 BPM（1 拍 6 行）、ループ 7.3 秒から 59.3 秒。Narshe 110 BPM、ループ 17.4 秒から 69.8 秒
- 曲番号 2 以降を変換するとき、その曲の情報を表示（最初の表示は 1 曲目のもの）
- NES の回帰テストは変化なし（1 拍 6 行の判定は NES の 2 曲、ループの判定は NES の 3 曲を変えたので SPC だけにした）
