# SPC（スーパーファミコン）の MIDI 化 計画（2026-11-03、コード変更なし）

## NSF / GBS との違い

| | NSF / GBS | SPC |
|:---|:---|:---|
| 音源 | 矩形波・三角波・ノイズ（音程はレジスタから計算） | 8 ボイスのサンプル再生（BRR 形式の波形を任意の速さで再生） |
| 音程 | 周期レジスタ → そのまま周波数 | ピッチレジスタは「元の速さの何倍で再生するか」だけ。**音程を出すにはサンプル自体の音高が必要** |
| 発音 | 周期上位レジスタの書き込み・音量の立ち上がりなどから推定 | **KON（キーオン）レジスタがある**ので発音の開始ははっきり分かる |
| 音色 | duty 比程度 | ボイスごとに使うサンプル番号（SRCN）。曲の途中で変わる |
| ドラム | ノイズ・DPCM | ドラムのサンプル（キック・スネア・ハイハット…）を普通のボイスで鳴らす。ノイズ発生器もある |
| 再生 | INIT / PLAY を 1/60 秒ごとに呼ぶ | SPC700 という CPU がずっと動き続け、タイマーを見ながら DSP レジスタを書く |
| ファイル | 曲データ＋ドライバ | **APU のメモリ 64KB とレジスタのスナップショット**（ある瞬間の状態から再開） |

## 全体の流れ（案）

1. **SPC を読む**: 64KB の RAM・DSP レジスタ・SPC700 のレジスタ、ID666 タグ（曲名・長さ）
2. **SPC700 をエミュレートして DSP への書き込みを記録**（NSF の 6502 と同じ考え方）
   - KON / KOFF、ピッチ（P）、サンプル番号（SRCN）、音量（VOL L/R）、ADSR / GAIN、ノイズ（NON）
3. **サンプルの音高を推定**: サンプル表（DIR）から BRR を復号し、ループ部分の 1 周期を自己相関で求める
   （DPCM の音程推定 v0.1.24 と同じ方法）。音高 = 32000 Hz ÷ 周期 × P / 0x1000
4. **ノート化**: KON = 発音開始。終わりは KOFF・次の KON・エンベロープが 0 になる所・ループしないサンプルの終わり
5. **トラック分け**: ボイス N → MIDI ch N（morokoshi の SPC のチャンネルボタン 1〜8 と同じ）。
   **同じボイスでサンプルが変わったら別トラック（同じ ch）**（ユーザー案。DPCM の音程付きトラックと同じ形）。トラック名は「Ch3 S12」のようにサンプル番号（楽器名は Sibelius が楽器と誤認するので使わない）
6. **ドラム**: サンプルごとに打楽器かどうかを判定し、GM のノート番号に置き換える（下記）
7. **テンポ・拍子・ループ**: NSF と同じ tempo.py / loop.py / meter.py を使う（発音時刻を 1/60 秒単位などに直して渡す）

## ドラムの考え方

- 判定は **サンプル単位**（同じサンプルは同じ打楽器）。特徴:
  - ループしない（または短いノイズのループ）、音の長さ、明るさ（ゼロ交差・スペクトル重心）、音程のはっきりさ（自己相関の強さ）
  - 低くて短い → キック、中域でノイズ的 → スネア、高くて短い → ハイハット、高くて長い → クラッシュ・ライド
  - 音程がはっきりしていて減衰する音を複数の音程で鳴らす → タム（音程付き。NES の下降音ドラム・DPCM の音程付きトラックと同じ扱い）
- ノイズ発生器（NON）を使うボイスはハイハット・シンバル系
- 判定は経験則なので、**サンプル番号 → GM ノートの上書き指定**を用意（NES の `--drum-map` と同じ考え）
- 出力: ドラムと判定したサンプルは、そのボイスの ch の「ChN Drums」トラック（NES のノイズ ch4・DPCM ch5 と同じ考え）。
  まとめて ch 10 に出すかは要相談

## 技術的な課題

- **SPC700 の速さ**: CPU が常に動き続ける（約 100 万命令/秒）ので、Python では NSF の 8 倍前後の処理量。
  ドライバはタイマー待ちのループで多くの時間を使うので、**待ちループを検出して時間を飛ばす**ことで速くできる見込み。
  遅すぎる場合の代案: morokoshi 用に改造している libgme の DLL に「DSP への書き込みを記録する」機能を足す（ただし nsf2mid 単体の配布物にも DLL が必要になる）
- **サンプルの音高のオクターブ誤り**: 自己相関は 1 オクターブ上下に間違えやすい（DPCM と同じ）。サンプルごとの移調指定（GUI で直せる形）を用意する
- **エンベロープ**: ADSR / GAIN を模型化しないと音の終わり（ゲート）が分からない。最初は KOFF・次の KON までとし、必要に応じて模型化
- **ビブラート・ポルタメント**: ピッチレジスタが連続で変わる。NES と同じく半音未満の揺れは同じ音、半音を超えて留まれば新しい音
- **テンポの単位**: NES の「1/60 秒の PLAY」がない。ドライバのタイマー（T0 など）の周期を「フレーム」として使えるか調べる。ダメなら 1/60 秒に直す
- **エコー・ピッチモジュレーション**: MIDI には出さない

## 進め方（段階）

1. **試作・調査**: SPC の読み込み、BRR の復号とサンプル表、SPC700 の模型と DSP 書き込みの記録。速さを測る。
   libgme で 1 ボイスずつ鳴らした音と、記録から出した音程を比べる（NES の拡張音源と同じ確認方法）。対象: スーパーマリオワールド・FF6・クロノ・トリガー など代表的なドライバ
2. **ノート化とトラック分け**（ボイス × サンプル）
3. **ドラム判定**
4. **テンポ・ループ・拍子**（既存の仕組みにつなぐ）
5. **GUI**（nsf2mid で .spc / SPC 入りの zip を開く）と morokoshi の Save → MIDI

## ユーザーに確認したいこと

1. MIDI ch はボイス番号（1〜8）でよいか。ドラムは各ボイスの ch のドラムトラックか、ch 10 にまとめるか
2. トラックを分ける単位は「ボイス × サンプル番号」でよいか（同じサンプルで音量・エンベロープだけ変わる場合は分けない）
3. サンプルの音高（オクターブ）は自動推定＋手動補正でよいか
4. 最初に確認する曲（正解を耳で判定できる曲）の候補
